Tutorial: build a notes backend with keel

A notes API over Postgres and nothing else — config, logging, migrations, auth, search, jobs and graceful shutdown. About 30 minutes.

0. Prerequisites

Go 1.26 or later, and Docker for the local Postgres. Fetch the module:

go get github.com/ManavA/keel

1. Scaffold the example

keel new copies a template profile into a project. The minimal profile is a notes API built out of keel, meant to be read rather than deployed:

go run ./cmd/keel new mynotes
cd mynotes
make run-local

make run-local starts a Postgres in Docker, points the service at it and serves on :8080. Against a database you already have:

DATABASE_URL='postgres://user:pass@localhost:5432/db?sslmode=disable' go run ./examples/minimal

Only DATABASE_URL is required. Every other default is chosen so the service comes up with none of them set.

2. Walk through the wiring

The service entry point (main.go) follows the same order every keel service follows:

  1. Logger first. log.New returns a JSON slog handler carrying request ids, with credential-shaped keys redacted. Development runs at Debug so verification links are walkable from the terminal; production stays at Info where they are never written.
  2. Load config. config.Load(&cfg) reads a struct from the environment, calls Validate if it implements it, and trims whitespace from secret and URL fields. Log it back with config.Redacted: secrets are replaced, URLs keep their host and lose their password.
  3. Open the app. app.New(app.Options{...}) holds the pool, migrations, routes, checks and jobs. Register health checks and scheduled jobs on the options, then Open. Migrations ride embedded in the binary (//go:embed migrations/*.sql), so there is never a question of which schema a build carries.
  4. Mount auth next to the API. The auth package owns its routes under /auth (signup, login, verify-email, forgot/reset, refresh, logout). Notes handlers check the session token and scope every query — listing, search and all — to the calling account.
  5. Index inline, notify by event. Notes are written to Postgres and indexed in the same request, so listing and search agree. The side effect that may be missed — a notification — goes out as a note.created event on the in-memory bus. A reconcile job rebuilds the index on an interval, which is what repairs an index left stale by a failed write.
  6. Run and shut down cleanly. a.Run(ctx) serves until SIGINT or SIGTERM, then finishes the requests already in flight. /healthz checks nothing; /readyz checks the pool and the index.

3. Exercise it

curl -s localhost:8080/readyz

TOKEN=$(curl -s -X POST localhost:8080/auth/signup \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"password123"}' | python3 -c 'import sys,json; print(json.load(sys.stdin)["token"])')

curl -s localhost:8080/api/notes \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"title":"Roof repair quote","body":"Slate tiles, south side"}'

curl -s 'localhost:8080/api/notes?limit=2' -H "Authorization: Bearer $TOKEN"
curl -s 'localhost:8080/api/notes/search?q=tile' -H "Authorization: Bearer $TOKEN"

Every notes request needs the bearer token; without one the API answers 401. Listing pages by keyset, so a note written while paging cannot shift a row across a page boundary — hand back next_cursor and nothing else.

4. Grow from here

  • Swap a default for an external backend by configuration, not a rewrite: Meilisearch for search, Postmark for mail, Cloud Pub/Sub for events. The showcase lists every default and option.
  • Add a second concern (an admin router, a new job) the way the example adds auth: another mount on the same app, sharing the pool.
  • When a check could pass without exercising what it names, write the case that must fail — the test suite treats a self-skipping database test as a failure under KEEL_REQUIRE_DB=1.
